# Engineering Skills & Workflow Standards (voicechat)

Expectations for contributors to the voicechat Go service.

---

## Project Domain Skills

- WebSocket services: one writer per connection, pings, cancelling work when a peer goes away.
- Streaming HTTP clients: OpenAI-style SSE chat completions, NDJSON audio, multipart uploads.
- Speech pipelines: STT, LLM, and TTS latency, chunking text for speech, and LLM prefix caching.
- Chinese, Japanese, Korean, and English text, rune by rune rather than byte by byte.

---

## Go Engineering Standards

- Idiomatic Go; run `make format` (`gofumpt` and `goimports`).
- Handle errors explicitly. Errors sent to the page name the stage that failed and say what went wrong.
- Comment intent, never what the code already says. One line on a declaration, longer reasoning in the body. Past two lines, make the code clearer instead.
- Use `context.Context` for everything a turn starts, so a cancel, a new turn, or a dropped connection stops it and aborts its backend requests.
- Do not leak goroutines or allocate needlessly.
- Never log what was said: no transcripts, prompts, or replies. Timings and outcomes only.
- Keep non-test files under 300 LOC, never over 500. Split larger ones. Test files may run longer for table coverage and fixtures.

---

## Testing & TDD Expectations

- Pair every source file with a test file: `foo.go` ↔ `foo_test.go`.
- Cover typical and edge cases.
- Use **table-driven tests** for core logic.
- Test against fake STT, LLM, and TTS servers (`httptest`) and a real WebSocket client, never live services.
- `speech_test.go` pins the chunker, markdown stripping, language detection, and history trimming, quirks included; changing an expected value is a deliberate change of behaviour and goes in the README.
- Follow **TDD**: write tests first, and watch them fail before implementing.

---

## Documentation Quality

- Reflect every behavioral, protocol, and configuration change in `README.md`.
- Keep the protocol in `README.md` and `index.html` in step with the server.
- Markdown prose must not use hard line breaks: keep each paragraph and list item on a single source line and let renderers wrap. Code blocks and tables are exempt. Markdown files must not contain tabs.

---

## Contribution Workflow Norms

- **Commit as soon as `make all` passes.** Do not wait to be asked.
- Sign every commit.
- One commit per logical change, tests and docs included. Fold fixups into the commit they belong to.
- Follow **Conventional Commits**, with a subject under 72 characters.
- Add a body only when the subject and diff leave the *why* unclear; keep it under five lines and state the reason, not a rundown of the changes.
- **No AI/agent attribution anywhere in the repo.** No `Co-Authored-By`, `Generated by ...`, or similar in commits, PRs, issues, or docs.
- Do not break the page–server protocol without updating both sides in the same change.
- Push and file PRs against `origin` unless told otherwise.

---

## Quality Gates

- `make all` must pass before merging.
- Hold coverage at or above `main`. Get approval for any gap.
- Refactoring must preserve behavior.

---

## Task Tracking Process

When working through review findings:

1. **Prepare `TODO.md`** - numbered, categorized items with `- [ ]` checkboxes.
2. **Make changes** - implement the selected items.
3. **Validate** - `make all` passes.
4. **Commit** - source changes only, never `TODO.md`.
5. **Mark complete** - check the items off with `- [x]`.
